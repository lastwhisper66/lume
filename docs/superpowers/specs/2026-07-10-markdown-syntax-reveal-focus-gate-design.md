# Markdown 语法揭示焦点门控设计

## 问题

打开 Markdown 文件时，ProseMirror 会自动创建一个位于文档首个可编辑位置的默认选区。当前 `syntaxReveal` 插件只根据 `EditorState.selection` 生成 Markdown 语法符号 decoration，没有判断编辑器是否真正获得焦点。因此，当文件首行是标题时，即使用户没有点击正文，首行也会显示 `#`，看起来像已经进入编辑状态。

## 期望行为

- 首次打开 Markdown 文件时，所有 Markdown 语法符号保持隐藏。
- 切换标签页时，新标签页在用户尚未聚焦正文前保持完整渲染状态。
- 用户通过鼠标或键盘实际聚焦编辑器后，继续按当前选区揭示对应 Markdown 符号。
- 编辑器失去焦点后，所有揭示符号立即隐藏。
- 不改变每个标签页保存的 ProseMirror 选区、历史记录、文档内容和 Markdown 序列化结果。

## 方案

使用 ProseMirror 在编辑器获得焦点时自动添加的 `.ProseMirror-focused` 类作为唯一焦点信号。在编辑器样式中增加规则：当 `.ProseMirror` 不包含该类时，隐藏其内部所有 `.md-marker`。

现有语法揭示插件仍根据选区生成 decoration。焦点门控只控制这些 decoration 的可见性，不引入 focus/blur transaction，也不把临时 UI 状态写入各标签页的 `EditorState`。

选择 CSS 门控的原因：

- ProseMirror 已负责维护焦点类，状态来源与实际 DOM 焦点一致。
- 打开文件和切换标签页时不需要主动重置选区或插件状态。
- 点击聚焦和失焦时由浏览器样式立即更新，不需要额外 transaction。
- 同一规则覆盖标题、引用、行内强调、链接等全部 `.md-marker`。

## 未采用的方案

- 在插件中用 transaction 保存 focus/blur 状态：会产生与文档编辑无关的 state 更新，并增加标签页销毁、恢复时的状态清理负担。
- 打开文件时移动或清除默认选区：不能解决“选区存在但编辑器未聚焦”的根本区别，并可能破坏标签页选区恢复。

## 测试与验证

本次修复不添加测试代码。修改样式后运行类型检查和生产构建，具体交互由用户手动验证：

1. 打开首行为标题的 Markdown 文件，`#` 不显示。
2. 点击标题行，`#` 显示。
3. 点击侧栏、标签栏或其他非编辑区，`#` 隐藏。
4. 切换到另一个首行为 Markdown 语法节点的标签页，未聚焦正文时不显示符号。
5. 再次聚焦正文后，当前选区对应的块级和行内符号正常显示。

## 非目标

- 不改变语法揭示的选区命中算法。
- 不调整 Markdown 符号的颜色、间距或动画。
- 不改变文件打开、标签页切换和保存流程。
